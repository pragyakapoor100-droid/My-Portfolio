The Situation

The client was a B2B SaaS company offering project management tooling for creative agencies. They had been investing seriously in SEO for 18 months — a content manager publishing two long-form articles per week, a backlink outreach campaign running in the background, and a recently hired marketing manager who "knew SEO was important." Yet their Google Search Console showed a consistent flatline: zero ranking, negligible impressions, and a sitemap that Google had partially processed but barely acted on.

The marketing manager suspected the problem was link authority. The CEO suspected it was the wrong keywords. Both were wrong. The problem was that Google could not read the site at all.

"18 months of content, zero indexed pages. The site wasn't being ignored — it was genuinely invisible."

Root Cause: JavaScript Rendering

The platform had been built as a React single-page application (SPA) with client-side rendering. This is an extremely common architecture in SaaS products — but it creates a serious SEO problem when implemented without server-side or dynamic rendering support.

When Googlebot visits a client-side rendered page, it receives an almost empty HTML shell. The actual content — headings, paragraphs, meta tags, links — is injected by JavaScript after the page loads. Googlebot does have the ability to render JavaScript, but it does so in a second wave, often days or weeks after the initial crawl, using a headless Chromium instance. For a site with low domain authority and no established crawl frequency, this two-wave rendering delay meant Google rarely got to see the actual content at all.

I confirmed this in the first hour of the audit using the GSC URL Inspection tool, which showed a "Crawled - currently not indexed" status for every URL tested. The rendered HTML snapshot shown in the tool was the empty shell — just a <div id="root"></div> with no content inside.

Audit Scope

Given the scale of the indexing problem, I focused the audit in three layers:

Layer 1 — Rendering & Indexability

Full rendering audit using a combination of GSC URL Inspection, manual curl requests to compare raw server HTML against browser-rendered HTML, and Screaming Frog's JavaScript rendering mode. I also used Cloudflare Workers to intercept bot user-agent requests and log what the server was returning to Googlebot specifically.

Layer 2 — Architecture & Internal Linking

Sitebulb crawl of all 94 planned site pages (as listed in the XML sitemap) to map internal link structure, anchor text distribution, and crawl depth from the homepage. I also cross-referenced the sitemap submission history in GSC to understand which URLs had been discovered vs. processed vs. indexed over time.

Layer 3 — Core Web Vitals

WebPageTest runs on the five highest-priority pages in both mobile and desktop configurations, with CrUX field data pulled for any URLs with sufficient traffic. LCP, CLS, and INP measured and traced to specific causal elements.

Key Findings

01

Client-Side Rendering With No Fallback

Every page on the site returned an empty HTML shell to any client — including Googlebot — that did not execute JavaScript. No server-side rendering (SSR), no static generation (SSG), and no dynamic rendering in place. The entire content layer of the site existed only in the JavaScript bundle. Googlebot's first-wave crawl, which reads only raw HTML, saw nothing indexable on any page.

02

Meta Tags Rendered Client-Side

Title tags, meta descriptions, and Open Graph tags were all being injected by a React Helmet implementation — meaning they were also absent from the raw HTML. Even on the occasions where Googlebot did execute the JavaScript in its second wave, it was encountering meta tags with generic fallback values because the dynamic meta tag injection was dependent on API calls that took over 4 seconds to resolve.

03

Navigation Links Not Crawlable

The site's main navigation used React Router with client-side link handling. The actual <a href> attributes were being overwritten by JavaScript event handlers, meaning the raw HTML contained no standard hyperlinks for Googlebot to follow. Each page was effectively an island — even if Google had indexed the homepage, it had no way to discover any other URL through standard link crawling.

04

LCP of 3.2 Seconds (Mobile)

The largest contentful paint on mobile was a hero image loaded as a high-resolution PNG without preloading, combined with the JavaScript bundle (1.4MB uncompressed) blocking the render thread. Even after fixing the indexing issue, poor CWV would suppress rankings for competitive queries.

The Fix Plan

I delivered a technical audit report to the client's CTO and marketing manager, followed by a 2-hour implementation workshop. Given the engineering effort required, I prioritised fixes into two tiers:

Tier 1 — Quick Wins (No Framework Changes Required)

  1. Dynamic rendering via Prerender.io: Deployed a rendering proxy that detects bot user agents and serves pre-rendered HTML snapshots instead of the JavaScript shell. This was a one-day engineering task and immediately made all 94 pages readable to Googlebot without touching the React codebase
  2. Static meta tags in <head>: Critical meta tags (title, description, canonical) hardcoded into the server-side HTML template as fallbacks, ensuring they were present even before JavaScript execution
  3. Href attributes on navigation links: React Router links updated to include proper href attributes alongside the JS event handlers, enabling Googlebot to crawl links via standard anchor discovery

Tier 2 — Structural Improvements (Phased Over 6 Weeks)

  1. Image optimisation: Hero and feature images converted to AVIF with <link rel="preload"> in the document head — LCP dropped from 3.2s to 0.8s
  2. Bundle splitting: JavaScript bundle split into route-based chunks using dynamic imports, reducing initial JS payload from 1.4MB to 280KB
  3. Internal linking infrastructure: A structured blog → feature page linking system built into the CMS template, ensuring every blog post links to at least two relevant product feature pages
  4. XML sitemap refresh: Sitemap regenerated and resubmitted to GSC after all fixes went live, triggering a fresh crawl cycle

What I Learned

JavaScript-rendered sites are one of the most common and most invisible SEO problems in the SaaS and tech startup world. Every engineer building with React, Vue, or Angular knows what they're doing — but very few think about what the site looks like to a bot that may never execute that JavaScript at all.

The fastest fix here was not rewriting the application in Next.js (though that would be the ideal long-term solution). It was getting a rendering proxy in front of bots within 48 hours of the audit landing, so Google could start indexing while the engineering team tackled the deeper structural work at a pace that didn't disrupt their product roadmap. Speed of partial implementation beats perfection that takes months.
